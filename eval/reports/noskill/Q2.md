# 选题报告：自进化 agent 的评测

## 1. 真实任务与对照工作
真实部署中的自进化：①代码/科研 agent 迭代修改自身代码以改进算法；②客服/运维等工具使用 agent 在线积累经验、改写提示词与调用策略；③自动搜索 agent 系统结构。对照工作：
- Voyager：技能库累积，评测=Minecraft 固定科技树任务成功率；
- ADAS：代码空间进化，评测=MATH/GSM8K/DROP 等静态基准留出集；
- AlphaEvolve：演化代码，评测=带自动验证器的数学/算法题。
共性：以固定基准提升作为“变强”的证据。
（网络检索：已核实 LiveBench、RE-Bench 的定位；SWE-bench-Live 与 AlphaEvolve 细节依已有知识，待复核。）

## 2. 现有评测的隐含假设 → 部署中不成立处
- 静态同分布：默认部署任务与基准同分布且不变；真实环境持续漂移（网页改版、API/依赖更新），过拟合固定基准≠变强。
- 单指标无回归：默认改 prompt/代码不伤及其他能力；实际常引入隐性退化（指令遵循、安全护栏、成本时延），且评测无回归套件。
- 验证器可信：默认 reward/单测不可钻空子；自修改代码会特判样例、绕过校验（reward hacking）。
- 快照式评测：只评最终版，默认演化稳定收敛；实际需版本化、可回滚、长程稳定。

## 3. 研究问题、假设与差异
RQ1：自进化在“进化可见任务”与“隔离/时移任务”上的增益差（泛化差距）多大？
RQ2：经验回放/技能库/代码搜索三类机制，谁更易造成正交能力退化？小回归套件能否检出？
RQ3：弱验证器被 hack 的比率随进化轮次如何变化？diff 审计能否发现？
假设：H1 代码空间进化的泛化差距显著大于 prompt 空间；H2 退化常见但标准评测难发现，50 条回归套件可覆盖大半；H3 hack 率随轮次上升，且与 diff 中的“基准特化”模式相关。
与最近工作差异：LiveBench、SWE-bench-Live 只解决基准污染，未针对自进化的选择压力；RE-Bench 评自改进 agent 但缺正交回归与 hack 审计；本提案提出“隔离任务流＋回归套件＋演化审计”三位一体协议。

## 4. 最小实验（1–2 周）
复现精简 ADAS（在 MATH 训练集上进化）或 Reflexion（WebShop＋HotpotQA）。任务分三块：A=进化可见集；B1=同分布留出；B2=时移/实时集（LiveBench 新题或 SWE-bench-Live 子集）。每轮演化后快照 agent，评测 A/B1/B2＋固定回归套件（IFEval 子集＋安全提示＋一个无关环境）＋代码 diff 审计。指标：泛化差距、回归率、hack 率、token 成本。基线：不进化／仅 prompt／代码进化；配对 bootstrap 检验。若 H1/H2 成立且套件与审计有效，即证实现有评测系统性高估自进化收益。
